# Task Tracker API

[![CI](https://github.com/nyrok8/task-tracker/actions/workflows/ci.yml/badge.svg)](https://github.com/nyrok8/task-tracker/actions/workflows/ci.yml)

API модуля трекера рабочих задач для медицинской информационной системы (МИС):
персонал ставит себе разовые и периодические задачи — операции, обходы пациентов,
звонки, отчёты.

## Стек

- **Ruby** 3.4.4
- **Rails** 8.1 (API-only)
- **PostgreSQL**
- **dry-validation** — валидация запросов, **Ransack** — фильтрация списков,
  **ice_cube** — раскрытие правил повторения
- **RSpec** + FactoryBot; **rspec-openapi** — генерация OpenAPI-доки (`swagger/`)

## Как запустить

### Docker

```bash
docker compose up --build
```

API поднимется на `http://localhost:3000`. База создаётся, мигрируется и
наполняется сидами (системные теги) автоматически при первом старте.

### Локально

Нужны Ruby 3.4.4 и PostgreSQL.

```bash
bundle install
bin/rails db:create db:migrate db:seed
bin/rails server
```

Тесты и линтер:

```bash
bundle exec rspec
bin/rubocop
```

### Примеры запросов

Разовая задача:

```http
POST /tasks/one_offs
Content-Type: application/json

{ "one_off": { "name": "Patient call", "description": "Discuss lab results", "scheduled_at": "2026-06-12T10:00:00" } }
```

Периодическая — ежедневный обход в 09:00:

```http
POST /tasks/recurring/templates
Content-Type: application/json

{
  "template": { "name": "Ward rounds", "description": "Morning ward rounds", "scheduled_at": "2026-06-01T09:00:00" },
  "rule": { "recurrence_type": "daily", "starts_on": "2026-06-01", "day_interval": 1 }
}
```

Единый список за окно (фильтры: `q[status]`, `q[statuses][]`, `q[tag]`,
`q[assignee_id]`, `q[query]`, `q[template_id]`):

```http
GET /tasks?from=2026-06-12T00:00:00&to=2026-06-12T23:59:59
```

Полное описание эндпоинтов — в `swagger/*.openapi.yaml`.

## Как устроены задачи

Задачи двух типов разведены в **два независимых write-домена** с **единым чтением**:

- **Разовая** (`Tasks::OneOff`) — обычная запись с собственными
  `scheduled_at` и `status`. Классический CRUD.
- **Периодическая** (`Tasks::Recurring::*`) — **шаблон** (`Template`,
  create-only: после создания не редактируется) плюс **правило** (`Rule`) с
  параметрами повторения. Изменения отдельных повторений идут через `Override`
  (см. «Исключения из правил»).

Типы правил (`Rule.recurrence_type`):

| тип | смысл |
| --- | --- |
| `daily` | каждый n-й день |
| `monthly_day` | фиксированное число месяца, 1–31 (для коротких месяцев берётся последний день) |
| `month_parity` | только чётные или только нечётные числа |
| `specific_dates` | только перечисленные даты |

Правило стартует с `starts_on` и ограничивается `ends_on` **или** `max_count`
(если оба пусты — бессрочное).

**`GET /tasks`** — единственная точка, где оба домена встречаются: разовые
задачи сливаются с развёрнутыми повторениями за запрошенный период в один
список, отсортированный по `scheduled_at`. Каждый элемент несёт `kind`
(`one_off` / `occurrence`) и свою идентичность: `id` у разовой,
`template_id` + `date_key` у повторения.

У повторения два «дата-поля» с разными ролями:

- **`scheduled_at`** — бизнес-время: когда задача реально назначена. По нему
  работают окно списка, фильтры и сортировка.
- **`date_key`** — идентификатор экземпляра (вместо бессмысленного для
  нехранимых строк auto-id). Им экземпляр адресуется в URL, и он не меняется
  даже при переносе задачи на другой день.

## Проблема бесконечности

Бессрочное правило («ежедневный обход» без даты окончания) — это потенциально
бесконечный ряд задач. Хранить его строками нельзя, поэтому **экземпляры
повторений не материализуются вообще**: в базе живут только шаблон, правило и
точечные отклонения.

Список строится на лету для запрошенного окна:

1. `DatesCalculator` раскрывает правило в даты, попавшие в окно.
2. Один SQL-запрос накладывает отклонения на шаблон
   (`COALESCE(override, template)`) и отдаёт готовые экземпляры.

Сколько бы лет ни «длилось» правило, стоимость запроса зависит только от ширины
запрошенного окна (а она ограничена — максимум 366 дней на запрос), и в базе от
этого не появляется ни одной лишней строки.

## Исключения из правил (бонусная задача)

«Отрыв» одного экземпляра от правила реализован через **`Override` — разреженную
дельту**, привязанную к `(template_id, date_key)`. Хранятся только отличия от
шаблона: `NULL` в колонке означает «наследовать из шаблона». Это даёт три
независимых механизма:

- **Своё состояние у каждого экземпляра.** Отметить «выполнено» обход за
  9 июня — это `status: done` в override этого дня; вчерашние и завтрашние
  повторения не затронуты.
- **Перенос одного экземпляра.** `scheduled_at` в override двигает конкретное
  повторение на другое время или день: «среду перенесли на 2 часа позже» или
  «на следующий день». `date_key` при этом не меняется — экземпляр остаётся
  адресуемым, а в списке он находится уже по новому бизнес-времени (выборка
  учитывает перенесённые в окно экземпляры, даже если их исходная дата в окно
  не попадает).
- **Удаление одного экземпляра.** Строку виртуального экземпляра не удалить —
  правило снова «родит» эту дату. Поэтому удаление — это tombstone
  (`deleted_at` в override): раскрытие пропускает такую дату. Отмена
  (`status: cancelled`, задача видна в списке) ≠ удаление (задачи в списке нет).

Работа с экземпляром идёт по его `date_key`. Выполнить обход только за 12 июня:

```http
PATCH /tasks/recurring/templates/1/overrides/2026-06-12
Content-Type: application/json

{ "override": { "status": "done" } }
```

Перенести обход 12 июня на 13-е, 15:00:

```http
PATCH /tasks/recurring/templates/1/overrides/2026-06-12
Content-Type: application/json

{ "override": { "scheduled_at": "2026-06-13T15:00:00" } }
```

Удалить только это повторение:

```http
DELETE /tasks/recurring/templates/1/overrides/2026-06-12
```
